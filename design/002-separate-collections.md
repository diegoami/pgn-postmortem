# F-13: separate collections and landing pages

Status: in review

Owner decisions (2026-10-01):

- The owner's book workspace owns the profile manifest; pgn-postmortem remains
  generic and supplies the API/CLI.
- The first visible titles are “Over-the-board games” and “Correspondence
  games”.
- The top-level landing page is generated by pgn-postmortem from profile
  metadata and descriptions supplied by the workspace.

Design revision (2026-10-01): make the workspace contract explicit before
review. The implementation will use a `CollectionProfile` value and a
`Workspace` builder, with the workspace output root as the only writable root.
Each profile's analyzed and site paths are resolved beneath that root, and the
landing page receives only profile summaries; no profile's games are passed to
another profile's `Collection.read` or `build_site` call. The existing one-site
CLI remains unchanged, while the new workspace command is additive.

## Problem

The owner needs to finish processing a real archive without blending unlike
playing contexts. Over-the-board games and correspondence games must be
separate collections, each with its own landing page, career totals, chapters,
quiz and game index. A later desktop application must consume this model; it
must not create a second data model.

This iteration is a workspace/orchestration layer around the existing
single-collection library. It does not process the owner's archive yet.

## Findings

- `Collection.read` accepts one or more paths and returns one flat collection;
  duplicate removal happens within that call (`pgn_postmortem/collection.py:299-351`).
  Passing OTB and correspondence paths together would therefore create exactly
  the mixing the owner wants to avoid.
- `Collection.build_site` delegates one collection to one output directory
  (`pgn_postmortem/collection.py:393-400`). Its existing behavior is the right
  collection-site primitive, but it has no workspace identity or landing page.
- The `site` CLI reads one collection and writes one site (`pgn_postmortem/cli.py:92-105`,
  `132-150`). The new workspace command must be additive; existing one-site
  commands and paths remain compatible.
- `build_site` already creates career/chapter/index output and removes generated
  stale pages (`pgn_postmortem/site.py:1590-1660`). A workspace must keep each
  collection in its own subdirectory so those cleanup rules cannot cross a
  collection boundary.
- Page links are relative and the site wrapper derives its stylesheet path from
  the page root (`pgn_postmortem/site.py:790-817`). A workspace landing page at
  the workspace root can link to `<slug>/index.html` without changing existing
  collection page links.
- The current project direction keeps the library generic and puts fetching,
  output plumbing and workspace configuration in a later pipeline layer
  (`CLAUDE.md:39-47`, `ROADMAP.md:14-15`, `docs/book-plan.md:32-39`). F-13
  needs only explicit local profiles and does not reopen the source/fetching
  design.

## Design

### Explicit profiles

Add immutable `CollectionProfile` and `Workspace` API values:

- `slug`: an ASCII URL/path slug, unique within the workspace;
- `title`: the visible collection title;
- `inputs`: PGN files, directories or globs for this collection only;
- `player` and `aliases`: the player identity for this collection;
- `analyzed_dir`: that collection's analysis cache;
- `site_dir`: its generated site directory relative to the workspace output;
- optional short description and source label for the landing page.

The workspace takes an ordered list of profiles. It validates all slugs and
paths before writing anything: slugs are non-empty, ASCII, stable and unique;
reserved `assets`/`index.html` collisions are rejected; and a profile cannot
write outside the workspace output. Profiles are the only boundary mechanism.
The implementation never guesses OTB versus correspondence from PGN headers.

The owner repository can construct profiles in Python or from a small local
configuration file. The F-13 implementation should choose one representation
and document it; the recommended default is a Python API plus a simple CLI
manifest, while fetching and remote credentials remain F-3.

### Build and output

Add a workspace builder and a `book`/`workspace` CLI command that, for each
profile in order:

1. reads only that profile's inputs;
2. writes/uses only that profile's analysis directory;
3. builds the existing site under `workspace/<slug>/`; and
4. records the profile summary for the workspace landing page.

The root output is:

```text
workspace/index.html
workspace/otb/index.html
workspace/otb/career.html
workspace/otb/chapters/...
workspace/correspondence/index.html
workspace/correspondence/career.html
workspace/correspondence/chapters/...
```

The landing page contains one card per profile with its title, description,
game count and link to `<slug>/index.html`. It does not aggregate games,
results, opponents, ratings or chapter scores across profiles. A collection's
existing pages link only within that collection and back to the workspace
landing page through an explicit home link.

The existing `site` command remains unchanged for users who want one collection
without a workspace. The desktop application is not part of F-13; it will later
call this same workspace API.

### Tests and owner check

Use hand-written fixtures with two profiles whose game IDs overlap and whose
results differ. Tests must prove:

- the profiles produce two separate sites and two separate landing cards;
- the overlapping game is retained once in each profile and never deduplicated
  across profiles;
- each profile's career/chapter/index counts contain only its own games;
- a profile with no analyzed games keeps its own career behavior and does not
  create broken chapter links;
- duplicate, invalid or traversal slugs fail before output is written;
- rebuilding removes generated pages only within the affected profile and
  preserves authored pages in other profiles;
- all workspace and collection links resolve, including the stylesheet and
  workspace-home links.

The owner reads an OTB landing page and a correspondence landing page before
merge and confirms that the collections are visibly separate. A negative
verdict returns the iteration to implementation.
