### Findings

1. **The done-when item "the design record … exist[s]" is skipped without saying so.** Non-blocking. r4 `ADOPT.md` §5.1–5.2 says to write `design/001-adopt-harness.md` and have it reviewed "(… Claude Code: a fresh-context session)" before writing files. §6 lists "the design record, the review records and the provenance exist". No `design/001-adopt-harness.md` is in the change, and no design issue or comment exists (`gh pr view 1 --comments` and `gh issue list` are both empty). But r4's authoritative rule says the opposite for this mode: `PRINCIPLES.md:73-75` says "A design record … exists only in OpenCode mode …; Claude mode has none, so it has no design records". `CLAUDE.md:19` says "There is **no design stage**". The r4 `README.md` says adoption "takes the bootstrap", and the bootstrap in Claude mode is one review. The fallback order at `PRINCIPLES.md:25-29` makes `PRINCIPLES.md` govern, so leaving the record out is correct and I don't block on it. What's wrong is that neither the PR body nor the commit message says the §6 item was deliberately not met, or why. Fix: add one sentence to the PR body saying the adoption ran in Claude mode, so under `PRINCIPLES.md:73-75` there is no design record. Separately, file the `ADOPT.md` ↔ `PRINCIPLES.md` contradiction upstream as a harness defect (per `PRINCIPLES.md:25-26`). r4's `ADOPT.md` also still names release `r3` at lines 5, 18 and 85. Don't fix either one in this repository.

2. **The `pages` row is listed as a gate, but it cannot stop a merge.** Non-blocking. The row at `CLAUDE.md:81` has `when` = "on push to `main` touching `examples/docs/**` or the workflow". `.github/workflows/pages.yml` triggers only on `push: branches: [main]` and `workflow_dispatch`, so it runs after the merge. That means it can never be the red gate that `PRINCIPLES.md:57` ("A red gate does not merge") relies on. The row also says `repeats` = 1 while its failure model says "re-run once before treating it as a defect", which is two runs. Suggestion: label it a post-merge deploy check, not a merge gate, and make the repeats column match the failure model. The two real merge gates are correct (see Verified).

3. **The slot declares parts of F-1/F-2 closed, while the book plan says nothing in it is agreed.** Non-blocking. `CLAUDE.md:102-106` puts the DeepSeek/bring-your-own-key prose provider and the book's chapter list under "decided, and not to be re-opened". But `docs/book-plan.md:3-5` says the plan "is not a shaped request, and nothing in it is agreed for implementation", and F-1 and F-2 are still `requested` and unshaped (`ROADMAP.md:11-12`). Both can be true: the owner fixed these directions while planning, and the user's own planning notes agree. Still, a later shaping session gets two different signals. Suggestion: in the `docs/book-plan.md` header, say that the choices recorded in the `CLAUDE.md` slot are settled and the rest is direction.

4. **The owner decisions have no recommended default or reason.** Non-blocking. `PRINCIPLES.md:109-111` says owner decisions are "Recorded with a recommended default, the reason, and an owner-decision mark". The PR body's "Owner decisions (2026-09-24)" table gives only `decision | value`: "release r4", "modes both", "`merge:` owner", "base a branch from `main`". Only `design:` and the `PLAN.md` split have any reasoning. The values themselves are recorded in the files that must hold them (`CLAUDE.md:48-50`, `CLAUDE.md:73-74`), and nothing in the adopted files contradicts them. The gap is incomplete records, not wrong ones. Add the default and the reason to each row.

5. **The owner quotes in the roadmap can't be checked against the repository.** Non-blocking. `ROADMAP.md:11-13` quotes the owner "verbatim", for example "first publishing a pip / python library that creates a wikipedia / epub from a pgn collection". None of these strings appear in the repository, in `book-poc:PLAN.md` or in `docs/book-plan.md`. They are consistent with the plan's milestones (`docs/book-plan.md` *Milestones* 1–3 map one-to-one onto F-1..F-3). Since `ROADMAP.md:25-26` says the wording is "quoted verbatim … and never silently reworded", the owner should confirm the wording when the first request is accepted. I could not reproduce these quotes, so I don't claim they are wrong.
